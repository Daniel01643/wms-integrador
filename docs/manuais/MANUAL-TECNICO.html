Manual Tecnico (Nivel 1)

Guia de operação do dia a dia para o técnico humano no servidor SRVAPPALC02 (Windows Server 2012 R2, PowerShell 4.0/5.1). O passo a passo pressupõe **acesso LOCAL ao servidor por RDP (Área de Trabalho Remota) ou direto na máquina, abrindo o PowerShell como Administrador** no próprio servidor. (Alternativa avançada: os scripts também rodam por WinRM com Invoke-Command, mas este manual foca no acesso local.)

Depois que o sistema está em produção, o técnico opera a partir do servidor. Todos os scripts de operação vivem de forma permanente em C:\Friozem\importacao_notas\tools\deploy — essa é a pasta de trabalho do dia a dia. Rode o PowerShell como Administrador, entre nessa pasta e use sempre:

cd C:\Friozem\importacao_notas\tools\deploy
powershell -ExecutionPolicy Bypass -File .\<script>.ps1 <parâmetros>

A instalação completa (criar as pastas, publicar a primeira release, configurar o serviço NSSM, compartilhar a entrada, virar para produção) não está aqui: ela vive em docs\INSTALACAO-SERVIDOR.md. Este manual cobre só a **operação recorrente no servidor. O C:\temp\deploy só aparece na primeira instalação** (ver o guia de instalação); no dia a dia use sempre tools\deploy.

0. Ambiente: servidor x máquina de build (local)

Há dois ambientes diferentes, e a maior parte das tarefas acontece só no servidor. Não confunda as pastas de um com as do outro.

Servidor SRVAPPALC02 (produção) — onde você opera no dia a dia

É onde o serviço roda e onde o técnico trabalha (via RDP). A estrutura do app fica em C:\Friozem\importacao_notas:

  • app\current — a release ativa (o NSSM aponta aqui); releases antigas em app\releases\<versao>.
  • config\ — appsettings.Production.json, email.settings.json e os dois TXT de destinatários (ACL restrita).
  • data\ — Estado (diário do pacote) e telemetria, fora do share.
  • logs\ — worker.out.log / worker.err.log.
  • backups\ — zips do current anterior a cada virada.
  • tools\deploy\ — os scripts de operação (servico.ps1, publicar-release.ps1, rollback.ps1, configurar-segredos.ps1, diagnostico.ps1, remover.ps1, etc.). É a **fonte de verdade** dos scripts no servidor.

A entrada compartilhada fica em C:\Friozem\kitbrf (share SMB kitbrf). Para operar: abra o PowerShell como Administrador no servidor e vá para C:\Friozem\importacao_notas\tools\deploy.

Máquina de build (local, opcional/avançado) — só para gerar nova versão

É o repositório com o código-fonte (src\) e os scripts-fonte (deploy\). Serve apenas para gerar uma nova versão quando houver mudança de código: rode deploy\publicar.ps1, que produz o .zip em artifacts\. A maioria das tarefas de operação NÃO precisa da máquina de build.

As pastas deploy\ e artifacts\ são do repositório local (máquina de build), não existem no servidor. No servidor, os scripts de operação ficam em tools\deploy (não em deploy\) e não há artifacts\. Se você está no servidor e vê uma instrução com deploy\ ou artifacts\, ela é da máquina de build — no servidor, o equivalente é tools\deploy.

2. Iniciar / parar / reiniciar / status do serviço

Use servico.ps1 a partir de C:\Friozem\importacao_notas\tools\deploy. O parâmetro -Acao é obrigatório e aceita exatamente Start, Stop, Restart ou Status:

cd C:\Friozem\importacao_notas\tools\deploy
powershell -ExecutionPolicy Bypass -File .\servico.ps1 -Acao Status
powershell -ExecutionPolicy Bypass -File .\servico.ps1 -Acao Start
powershell -ExecutionPolicy Bypass -File .\servico.ps1 -Acao Stop
powershell -ExecutionPolicy Bypass -File .\servico.ps1 -Acao Restart

O Status combina a saída de nssm status com Get-Service (mostra situação e tipo de inicialização). As ações são idempotentes (parar algo já parado não gera erro).

Pelo services.msc (interface gráfica): abra services.msc, localize o serviço Friozem-ImportacaoNotas, e use o botão direito para Iniciar / Parar / Reiniciar. É o mesmo serviço; prefira o servico.ps1 quando puder, pois ele usa o NSSM de forma consistente.

3. Ver e interpretar os logs

Os logs ficam em:

C:\Friozem\importacao_notas\logs\worker.out.log   (saída normal)
C:\Friozem\importacao_notas\logs\worker.err.log   (erros)

São gravados pelo NSSM, com rotação diária ou a cada ~10 MB. Abra com o Bloco de Notas, com o notepad, ou acompanhe o fim do arquivo no PowerShell:

Get-Content C:\Friozem\importacao_notas\logs\worker.out.log -Tail 50 -Wait

Linhas comuns e o que significam:

Linha no log Significado
Watcher iniciado. Entrada=... Processados=... Erro=... O serviço subiu bem e está observando a pasta.
Relatório do pacote salvo em <Html> e <Pdf>. Um pacote fechou e gerou relatório.
E-mail do pacote enviado. O e-mail de fechamento saiu.
E-mail não configurado; relatório salvo em <Pasta>. SMTP não configurado; o relatório ficou em disco (sem erro).
Falha ao enviar o e-mail do pacote: <Motivo> O envio falhou; veja o motivo (host/porta/credencial SMTP).
HTTP 401 no envio WMS (identificador=...); renovando token e repetindo uma vez. Erro de credencial/token do WMS. O sistema renova e tenta 1x; se continuar 401, as credenciais WMS__Usuario/WMS__Senha estão inválidas (ver seção 4).
Serviço não iniciado: corrija a seção 'Pastas' do appsettings. Configuração de Pastas inválida; o serviço não sobe até corrigir.
Resumo semanal enviado para ... O resumo semanal saiu.

Se muitas notas aparecem como Pendente ao mesmo tempo, geralmente o problema está no WMS (fila/processamento), não no integrador.

4. Trocar usuário e senha do WMS

As credenciais do WMS ficam, por padrão, em variáveis de ambiente de MÁQUINA WMS__Usuario / WMS__Senha. Troque com configurar-segredos.ps1 (ele nunca exibe os valores; se você não passar, ele pede sem eco), a partir de C:\Friozem\importacao_notas\tools\deploy:

cd C:\Friozem\importacao_notas\tools\deploy
powershell -ExecutionPolicy Bypass -File .\configurar-segredos.ps1 -Fase Homolog
  • -Fase aceita Homolog (padrão) ou Producao — é apenas um rótulo do que está sendo gravado.
  • Por padrão (-Escopo Maquina) grava nas env de máquina WMS__Usuario/WMS__Senha.
  • O script pergunta WMS Usuario e WMS Senha sem mostrar o que você digita. Deixar em branco pula aquele item (não apaga o que já existe).

Depois de gravar, REINICIE o serviço para que ele herde a nova variável de ambiente: ```powershell powershell -ExecutionPolicy Bypass -File .\servico.ps1 -Acao Restart ```

5. Trocar usuário / senha / remetente do SMTP

O SMTP vive em C:\Friozem\importacao_notas\config\email.settings.json. A forma recomendada é pelo mesmo configurar-segredos.ps1, que grava o bloco Email com os valores da casa (Host=smtp.friozem.com.br, Porta=587, UsarTls=false, Habilitado=true), a partir de C:\Friozem\importacao_notas\tools\deploy:

cd C:\Friozem\importacao_notas\tools\deploy
powershell -ExecutionPolicy Bypass -File .\configurar-segredos.ps1 -Fase Producao

O script pede, sem eco quando for segredo:

  • SMTP Usuario e SMTP Senha (SecureString).
  • SMTP Remetente — parâmetro -SmtpRemetente (ex.: kitwms@friozem.com.br).
  • SMTP Nome do remetente — parâmetro -SmtpRemetenteNome (campo RemetenteNome; padrão KitWms Integrador).
  • Destinatarios do fechamento, separados por ; — parâmetro -SmtpDestinatarios.

Você também pode editar direto o email.settings.json (campos Host, Porta, UsarTls, Usuario, Senha, Remetente, RemetenteNome, Destinatarios, EnviarQuando). O arquivo é recarregado ao salvar. Em produção os valores são smtp.friozem.com.br:587 com UsarTls=false.

Limitações do envio: suporta STARTTLS (587) e SMTP interno; não suporta TLS implícito (465) nem OAuth2.

6. Trocar o endpoint/URL do WMS (virada homolog → produção)

A URL do WMS é a chave Wms:BaseUrl em C:\Friozem\importacao_notas\config\appsettings.Production.json:

  • Homologação/validação: https://friozem.assistsoftware.com.br:8888/wmsapi/api
  • Produção (virada futura): a mesma URL sem a porta :8888 (confirme a URL exata de produção com o fornecedor do WMS antes da virada — ver lacunas no resumo).

Edite o valor no arquivo, salve e reinicie o serviço (servico.ps1 -Acao Restart).

7. Destinatários de e-mail (fechamento e resumo semanal)

São duas listas diferentes, cada uma num **arquivo de texto (TXT) dedicado e editável a quente: um e-mail por linha**; linhas em branco são ignoradas; linhas que começam com # são comentários. Os dois arquivos são relidos a cada envio — editar e salvar vale no próximo envio, sem reiniciar o serviço. As listas reais não são versionadas (ficam em config\, cobertas pelo .gitignore).

7.1. Fechamento do pacote — Email:CaminhoDestinatarios

O caminho do TXT de fechamento é a chave Email:CaminhoDestinatarios. Se vazia, o padrão do sistema é <telemetria>\destinatarios-fechamento.txt. Exemplo de arquivo:

# Destinatarios do fechamento do pacote — um e-mail por linha. '#' comenta.
operacao@friozem.com.br
gestor@friozem.com.br

Precedência e fallback do fechamento (nesta ordem):

  1. se o TXT tiver ao menos um e-mail, ele é usado (tem precedência sobre Email:Destinatarios);
  2. se o TXT estiver ausente/vazio, usa-se a lista Email:Destinatarios (separada por ; no JSON) apenas como fallback;
  3. se ambos estiverem vazios, o e-mail do pacote não é enviado e um aviso é registrado no log — mas o fechamento conclui normalmente (o relatório HTML + PDF é gerado assim mesmo).

Editar Email:Destinatarios no JSON (email.settings.json / appsettings.Production.json) é apenas o fallback do fechamento, não o mecanismo principal. O mecanismo principal é o TXT apontado por Email:CaminhoDestinatarios.

7.2. Resumo semanal — Monitoramento:CaminhoDestinatarios

O caminho do TXT do resumo semanal é a chave Monitoramento:CaminhoDestinatarios. Se vazia, o padrão do sistema é <telemetria>\destinatarios.txt. Exemplo de arquivo:

# Destinatarios do resumo semanal — um e-mail por linha. '#' comenta.
ti@friozem.com.br
gestor@friozem.com.br

O fallback é diferente do fechamento: se o arquivo do resumo estiver ausente, vazio ou ilegível, o resumo vai para o destinatário mínimo ti@friozem.com.br (não cai em não-envio) e um aviso é registrado no log.

7.3. Nota de servidor — apontar as duas chaves para config\

Os defaults do código caem em <telemetria>, que fica dentro de data\ — fora do share kitbrf. Para manter as listas num lugar previsível e protegido, recomenda-se apontar ambas as chaves para C:\Friozem\importacao_notas\config\ no appsettings.Production.json, por exemplo:

  • Email:CaminhoDestinatarios → config\destinatarios-fechamento.txt
  • Monitoramento:CaminhoDestinatarios → config\destinatarios-resumo.txt

Confirme os valores efetivos em produção antes de supor onde os arquivos estão (ver lacuna no resumo). Lembre que config\ tem ACL restrita (seção 13) e que as listas reais não são versionadas.

8.1. Arquivos não-XML (ExtensaoInvalida) e a flag Pastas:TratarNaoXmlComoErro

Quando um arquivo depositado na entrada não é .xml, ele não é uma nota: o sistema não chama o WMS para ele. A separação acontece na detecção (ao listar os candidatos do pacote), em três grupos:

  • XML (.xml): segue o fluxo normal de integração.
  • Temporários (em cópia): extensões configuráveis em Pastas:ExtensoesTemporarias (default .tmp, .temp, .crdownload, .part, .partial, .filepart, .!ut, .opdownload, .bak, .lock; também arquivos com atributo Hidden/System). São ignorados — nem processa nem move, ficam na entrada até a cópia terminar (um .tmp pode virar .xml). Comparação case-insensitive, com o ponto normalizado.
  • Não-XML definitivo: qualquer outra extensão. Com Pastas:TratarNaoXmlComoErro = true (default), o arquivo é movido para Erro\<pacote>\ExtensaoInvalida com um .motivo.txt ao lado e registrado no relatório. Com a flag em false, o não-XML definitivo é apenas ignorado (fica na entrada), como no comportamento legado.

Reflexos nas estruturas:

  • CategoriaErro.ExtensaoInvalida: nova categoria de erro; define a subpasta Erro\<pacote>\ExtensaoInvalida (reusa o mesmo mecanismo de mover + .motivo.txt das demais categorias).
  • StatusLinhaRelatorio.ArquivoIgnorado: novo status, com cor neutra/cinza (#6B7280, fora da paleta da marca) e rótulo "Arquivo ignorado (não é XML)". No resumo do relatório e do e-mail há um contador próprio "Arquivos ignorados". Esse status é um aviso, não uma falha de WMS: não conta como nota real (não infla Total nem Não integradas).

Regra de e-mail do pacote 100% não-XML: um pacote que só tem arquivos ignorados (nenhuma nota real, XML válido ou inválido-de-conteúdo) gera o relatório HTML + PDF normalmente, mas **não envia e-mail** (o log registra que o pacote não tinha notas, apenas arquivos ignorados). Um pacote misto (ao menos uma nota real) segue a política de e-mail normal, e os arquivos ignorados aparecem no relatório e no corpo do e-mail.

Limpeza forçada sob demanda — limpar-extensao-invalida.ps1: para apagar as pastas ExtensaoInvalida sem esperar o ciclo de 60 dias, use esse script a partir de C:\Friozem\importacao_notas\tools\deploy (ele é replicado para lá pelo instalar.ps1):

cd C:\Friozem\importacao_notas\tools\deploy
powershell -ExecutionPolicy Bypass -File .\limpar-extensao-invalida.ps1 -WhatIf
powershell -ExecutionPolicy Bypass -File .\limpar-extensao-invalida.ps1

Ele só remove pastas cujo nome-folha seja exatamente ExtensaoInvalida dentro de <Entrada>\Erro, com guardas de caminho (recusa raiz de drive, não segue junctions/symlinks), suporta -WhatIf (lista sem apagar) e pede confirmação s/n quando não usa -Force. Parâmetros: -Caminho (entrada, default C:\Friozem\kitbrf), -NomePastaErro (default Erro), -NomeCategoria (default ExtensaoInvalida) e -Force (pula a confirmação).

8.2. Ligar/desligar o envio da placa do veículo (I50:EnviarPlacaVeiculo)

O integrador pode enviar ao WMS, no payload I50, a placa do veículo de transporte lida do XML da nota em transp/veicTransp/placa. Esse envio é controlado pela chave I50:EnviarPlacaVeiculo na config não-secreta C:\Friozem\importacao_notas\config\appsettings.Production.json:

Valor Efeito
true (padrão) Envia a placa exatamente como está no XML (transp/veicTransp/placa).
false Envia a placa em branco (placaVeiculo = ""), como no comportamento anterior.

A placa é enviada como está no XML, sem maiúsculas/minúsculas forçadas, sem hífen e sem outras transformações além do básico.

Para desligar o envio, edite o arquivo e deixe a chave em false:

"I50": {
  "EnviarPlacaVeiculo": false
}

Para religar, volte a chave para true (ou remova-a: o padrão é true).

A chave também pode ser sobrescrita por variável de ambiente de máquina I50__EnviarPlacaVeiculo (dois underscores). Na dúvida, prefira editar o appsettings.Production.json.

Só envia se existir no XML. A placa só vai preenchida quando a nota traz transp/veicTransp/placa. Se o XML não tiver esse campo, a placa vai em branco mesmo com a chave em true (não é erro).

Depois de editar, REINICIE o serviço para a mudança valer: ```powershell cd C:\Friozem\importacao_notas\tools\deploy powershell -ExecutionPolicy Bypass -File .\servico.ps1 -Acao Restart ```

8.3. I60 (associação automática da nota de venda): desligada em produção

Situação: a I60 está desligada em produção (I60:Habilitada=false, padrão). O Plano A (a I60 associar sozinha a nota de venda ao DocCarga criado pela I50) foi **testado no WMS de homologação em 09/11 e 10/11 e está pausado, aguardando o fornecedor do WMS**. Nada foi para produção. Histórico completo em docs\wms-codigo-customizado\HISTORICO-PLANO-A.md.

  • Como ligar (somente em teste/homologação, com OK do responsável): defina I60__Habilitada=true (variável de ambiente, ou I60:Habilitada no appsettings) e reinicie o serviço.
  • Opções de diagnóstico (teste): I60__TipoOperacaoNota (padrão INE) e I60__QtdeVolumeZero (true envia qtdeVolume = 0, usado só para isolar a conferência de volumes).
  • Enviar só a I60 de um XML: --enviar-i60 <xml> no Worker; mostra o JSON e grava envio e resposta em envio-manual-i60\.
  • Em produção, mantenha I60__Habilitada=false.

8.4. Devolução (I40): tela de chaves, desligada em produção

Plano B da devolução: uma página web, hospedada pelo próprio serviço, onde o colaborador digita ou bipa as chaves de NF-e; o sistema acha o XML em Processados, monta a I40 e envia ao WMS. Está desligada (Devolucao:Habilitada=false) e nada foi ligado em produção. No homolog (10/11), a I40 como IMP sem placa deu "Registrado com sucesso" e o recebimento foi concluído.

Habilitar (somente com OK do responsável e depois do firewall, ver INSTALACAO-SERVIDOR.md):

  1. Defina Devolucao__Habilitada=true (variável de ambiente do serviço) ou Devolucao:Habilitada em config\appsettings.Production.json.
  2. Reinicie o serviço. No logs\worker.out.log deve aparecer "Tela de devolução ligada na porta 8085".
  3. Teste http://<servidor>:8085/api/saude (responde {"status":"ok"}).

Chaves (seção Devolucao):

Chave Padrão O que faz
Habilitada false Liga a tela. false: a porta não abre.
Porta 8085 Porta HTTP (escuta em todas as interfaces; sem login).
EnviarPlacaPadrao false Estado inicial do checkbox "Enviar placa do veículo".
TipoOperacaoNota IMP Tipo de operação com a placa desligada (sem placa nem motorista).
TipoOperacaoNotaComPlaca ICD Tipo com a placa ligada. No homolog ainda deu "Erro na criacao do controlador de veiculo" (provável cadastro de transportadora, motorista ou doca).
NomeMotorista vazio Motorista fixo cadastrado no WMS. Obrigatório só com a placa ligada; vazio devolve erro 503.
MaxChavesPorEnvio 30 Limite por envio.
PastaAuditoria vazio Vazio = <Estado>\devolucao.
InverterPartes false Validado no homolog; a variante invertida não é necessária.

Regra da placa: desligada, tipoOperacaoNota = TipoOperacaoNota, placaVeiculoPrevistoNota e nomeMotorista em branco. Ligada, tipoOperacaoNota = TipoOperacaoNotaComPlaca, placa obrigatória (informada na tela) e nomeMotorista = NomeMotorista.

Firewall: a tela não tem login. Libere a porta somente para a rede interna (comando de exemplo em INSTALACAO-SERVIDOR.md, seção 3.12).

Auditoria: um arquivo por dia, devolucao_yyyyMMdd.log, em Devolucao:PastaAuditoria ou <Estado>\devolucao. Uma linha por chave: data;ip;placa;chave;nota;status;transacao;mensagem. Sem senha nem JSON. Cada envio também aparece em logs\worker.out.log.

Isolamento: a tela tem o próprio servidor web dentro do serviço. Se a porta estiver ocupada ou houver erro, o log registra "Tela de devolução falhou e foi desligada" e a integração das notas continua normalmente.

Erros da API: 400 (pedido inválido: lista vazia, mais de 30 chaves, placa ausente com o flag ligado), 503 (NomeMotorista ou Pastas:Entrada não configurados), 500 (erro inesperado; veja o log).

Para desligar: Devolucao__Habilitada=false e reiniciar o serviço.

Teste no homolog nesta máquina: docs\ROTEIRO-TESTE-I40.md.

9. Publicar nova versão e rollback

O .zip da nova versão é gerado na máquina de build (ver seção 0), rodando o deploy\publicar.ps1 do repositório; o arquivo sai em artifacts\<versao>\. Copie esse .zip para o servidor (ex.: C:\temp) e faça o resto no servidor.

Publicar uma nova release (no servidor) com publicar-release.ps1, a partir de C:\Friozem\importacao_notas\tools\deploy. Informe a origem (-ReleaseZip ou -ReleaseDir, nunca os dois):

cd C:\Friozem\importacao_notas\tools\deploy
powershell -ExecutionPolicy Bypass -File .\publicar-release.ps1 -ReleaseZip C:\temp\rel.zip -Versao 2026.02.01-1
  • -ManterUltimas (padrão 5): quantas releases antigas preservar em app\releases.
  • Faz backup do current anterior em backups\current_<carimbo>.zip, copia a config, aponta app\current para a nova release e reinicia o serviço.
  • Também atualiza os próprios scripts em tools\deploy para acompanharem a release.

Rollback para uma release anterior com rollback.ps1, na mesma pasta:

cd C:\Friozem\importacao_notas\tools\deploy
powershell -ExecutionPolicy Bypass -File .\rollback.ps1
powershell -ExecutionPolicy Bypass -File .\rollback.ps1 -Versao 2026.01.15-1
  • Sem -Versao, usa a release anterior (a segunda mais recente por data).
  • Para o serviço, copia a config, reaponta current e reinicia.

Ambos aceitam -WhatIf para simular antes de executar.

Remover o serviço (raro; preserva as pastas por padrão) com remover.ps1, na mesma pasta:

cd C:\Friozem\importacao_notas\tools\deploy
powershell -ExecutionPolicy Bypass -File .\remover.ps1
# Remove o serviço E limpa app\/logs\, preservando data\/backups\/config\ (com confirmação):
powershell -ExecutionPolicy Bypass -File .\remover.ps1 -LimparPastas -Confirm

10. Estado e telemetria (não mexer)

O Estado (diário do pacote pacote-atual.jsonl) e a telemetria (telemetria.jsonl, servico.jsonl, ultimo-resumo.txt, resumos em resumos\) ficam **fora do share, previstos em C:\Friozem\importacao_notas\data. Eles ficam invisíveis** aos usuários de propósito.

  • Não edite nem apague esses arquivos com o serviço rodando: o diário é a fonte de verdade para retomar um pacote após reinício sem reenviar notas ao WMS; a telemetria alimenta o resumo semanal.
  • A limpeza automática nunca toca essas pastas.

Nota de configuração: o caminho físico de Estado/telemetria depende de Pastas:Estado/Monitoramento:CaminhoTelemetria. Para ficarem em C:\Friozem\importacao_notas\data (fora do share), esses valores precisam ser **caminhos absolutos** no appsettings.Production.json. Confirme o valor efetivo em produção antes de supor onde estão (ver lacuna no resumo).

11. O serviço não sobe — diagnóstico e TLS 1.2

Passos na ordem:

  1. Veja os logs (seção 3), especialmente worker.err.log. A mensagem Serviço não iniciado: corrija a seção 'Pastas' do appsettings. indica config de Pastas inválida (por exemplo Estado igual a Processados/Erro).
  2. Confirme as variáveis de máquina do WMS: o serviço lê WMS__Usuario/WMS__Senha das env de máquina; se foram gravadas e o serviço não reiniciou, ele ainda não as herdou — reinicie.
  3. Rode o diagnóstico (somente leitura, sempre termina sem erro), a partir de C:\Friozem\importacao_notas\tools\deploy:
   cd C:\Friozem\importacao_notas\tools\deploy
   powershell -ExecutionPolicy Bypass -File .\diagnostico.ps1

Ele checa serviço, host/porta do WMS (friozem.assistsoftware.com.br:8888), SMTP (smtp.friozem.com.br:587), a pasta de entrada e o share kitbrf, e lê o registro do SChannel (TLS).

  1. Falha de conexão HTTPS ao WMS (handshake/TLS): em Windows Server 2012 R2 o TLS 1.2 depende do SChannel do sistema. A habilitação é feita pelo instalador (instalar.ps1 -HabilitarTls12, reversível e com confirmação) — um passo de instalação/manutenção, não de operação do dia a dia. O procedimento completo está em docs\INSTALACAO-SERVIDOR.md (seções 3.6/6); siga o guia de instalação para esse ajuste. Não há uma mensagem fixa de "handshake" no log — o sintoma é a falha de conexão HTTPS ao WMS.

13. Avisos de segurança

  • Nunca versione nem compartilhe senhas (WMS ou SMTP). As credenciais do WMS ficam em env de máquina; o SMTP em email.settings.json, que está no .gitignore.
  • A pasta config\ tem ACL restrita (apenas Administrators/SYSTEM e a conta do serviço leem). Os scripts reaplicam essa ACL; não afrouxe as permissões.
  • Os scripts não exibem segredos no console nem nos logs — mantenha esse comportamento.
  • Prefira -WhatIf em scripts de escrita quando estiver em dúvida, para simular antes de aplicar.

14. Guia rápido: usar a IA de apoio

Se você decidir usar um agente de IA para diagnosticar falhas ou propor alterações, o guia completo (fluxo, mapa de arquivos, como diagnosticar e como propor mudanças com segurança) está em ./MANUAL-AGENTE-IA.md. Usar a IA é opcional: você decide.

Antes de aceitar qualquer sugestão da IA, confira estes guarda-rails:

  • Não versione nem exponha segredos do WMS/SMTP (as env WMS__* e o email.settings.json continuam sensíveis; nada de colar senha em prompt, log ou resposta).
  • Não ligue a I60 em produção (I60:Habilitada deve seguir false; testada no homolog, pausada aguardando o fornecedor; ver seção 8.3). Os dados fiscais vão na I50.
  • Valide mudança de código com build + test no repositório, fora de produção, antes de promover.
  • Não rode teste de carga em produção ou homologação sem o OK do responsável.
  • Config antes de código: prefira ajustar configuração (JSON e os TXT de destinatários) a mexer no código; e deixe a execução no servidor (restart, publicar, rollback) para o técnico humano.
